# 데이터베이스 설계 가이드

## 식별자 매핑

### 저장 목적

공급사 재고·요금 API는 지역으로 검색해주지 않고 **숙소 코드 목록을 받아 조회**한다.  
따라서 어떤 숙소를 물어볼지 우리가 미리 알고 있어야 하며, 그 목록의 출처가 공급사의 숙소 목록 API다.  
공급사 코드 ↔ 내부 식별자 매핑을 DB에 저장하는 것이 검색의 전제다.

### 매핑 대상

| 매핑 대상 | 공급사 쪽 키 | 내부 식별자 |
|-----------|-------------|------------|
| 숙소 | `(공급사, hotelCode / propertyId)` | 내부 숙소 ID |
| 객실 타입 | `(공급사, 숙소 코드, roomTypeCode / roomId)` | 내부 객실 타입 ID |

객실 타입 코드는 해당 숙소 안에서만 유일하므로 매핑 키에 숙소 코드가 반드시 포함되어야 한다.

### 불변 조건

- **같은 공급사의 같은 코드는 언제 조회해도 항상 동일한 내부 식별자를 반환**해야 한다
- 서로 다른 공급사의 상품이 실제로 동일 숙소여도 기본적으로 **각각 별도 내부 식별자**를 부여한다

### 저장 대상 범위

- 요금·재고의 원본은 항상 외부에서 실시간 조회하므로 DB에 적재하지 않는다
- 저장 대상은 **공급사 코드 ↔ 내부 식별자 매핑**만이다

### 매핑 갱신 전략

숙소 목록은 자주 바뀌지 않고, 재고·요금은 매번 바뀐다. 이 성격 차이를 갱신 전략에 반영한다.

- 매핑은 공급사의 숙소 목록 API(① 단계)를 호출해 만든다
- 언제 호출할지(앱 기동 시 1회 / 주기적 갱신 / 별도 명령) 판단 근거를 문서에 남긴다
