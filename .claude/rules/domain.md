# 도메인 모델 가이드

## 상품 구조

숙박 상품은 **숙소 > 객실 타입** 2단계로 표현한다.

- 개별 물리 객실(101호, 102호 등)은 노출하지 않는다
- 요금과 재고는 **객실 타입 단위**다 (`remainingRooms: 3` = 해당 타입 객실이 그날 3개 남음)
- 공급사는 요청 인원을 수용할 수 있는 객실 타입만 반환한다 (`adults + children <= maxOccupancy`)

## 연동 두 단계 구조

공급사 API는 성격이 다른 두 단계로 나뉜다.

| 단계 | 성격 | 변경 빈도 |
|------|------|-----------|
| ① 숙소 목록 | 숙소·객실 타입 전체 목록. 조건 파라미터 없음 | 자주 바뀌지 않음 |
| ② 재고·요금 조회 | 숙소 코드 목록을 받아 bulk 조회 | 호출마다 값이 달라짐 |

공급사는 **지역으로 재고·요금을 검색해주지 않는다.** 숙소 코드 목록을 직접 넘겨야 하므로, ①로 숙소 목록을 미리 확보해 두는 것이 조회의 전제다.

## 공급사별 요금 모델

### Supplier A
- 요금 방식: **날짜별 1박 단가** (`nightlyRate`) + 세금 별도 (`taxAmount`) — **net**
- 총액 계산: `Σ(nightlyRate + taxAmount)` for each night
- 에러 표현: HTTP 상태 코드 (`4xx` / `5xx`)
- 숙소 식별자: `hotelCode` / 객실 타입 식별자: `roomTypeCode`

### Supplier B
- 요금 방식: **숙박 전체 총액** (`totalPrice`) — 세금 포함(**gross**), 날짜별 단가 없음
- 에러 표현: **HTTP는 항상 200**, 응답 본문 `resultCode`로만 실패 전달
  - `"0000"` = 성공 / `"E4xx"`, `"E5xx"` = 실패 / `data == null` = 실패
- 숙소 식별자: `propertyId` / 객실 타입 식별자: `roomId`

> ⚠️ Supplier B는 장애 상황에서도 HTTP 200을 반환한다. `resultCode` 확인 없이는 장애를 정상으로 처리하게 된다.

## 공통 규약

| 항목 | 규약 |
|------|------|
| 인증 | 요청 헤더 `X-Api-Key: {key}` |
| 날짜 형식 | `YYYY-MM-DD` |
| 날짜 경계 | 체크아웃일은 숙박일에 **포함되지 않음** (9/1 체크인 / 9/4 체크아웃 = 3박) |
| 인원 | 요청은 `adults`, `children` 분리. `maxOccupancy`는 성인+아동 합산 기준 |
| 통화 | ISO 4217 코드 (`KRW`, `USD` 등) |
| 금액 | 통화 최소 단위 정수 (KRW는 소수점 없음) |
| 조식 | `breakfastIncluded` (boolean) — 재고·요금 API(②)에서만 제공 |
| 재고 | `remainingRooms` (정수) — 날짜별 잔여 객실 수 |
